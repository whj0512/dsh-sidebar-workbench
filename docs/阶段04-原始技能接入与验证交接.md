# 阶段 4 原始技能接入与验证交接

条目化技能由用户在实际运行的 DSH profile 中注册。用户已确认条目化主功能完成，后续构建与业务验证由用户执行。真实 V2 比较和采用待材料。 [阶段 4 验收记录](阶段验收/阶段04-P01-P02-P04.md)

## DSH 技能准备

用户自行下载技能，并在任务执行 preset 的 DSH 技能目录或其他技能提供方中注册。条目化入口使用 `requirement-itemizer`，委派角色默认使用 `requirement-chunk-segment` 和 `requirement-chunk-extract`。三个技能均需允许模型调用。使用 DSH 的 filesystem provider 时，注册名采用小写连字符格式并由技能 frontmatter 提供。 [DSH 技能目录与格式](../../deepseek-harness/packages/skill/skill-filesystem/README.md)

工作台只读取 DSH 注册表已经发现的技能。旧工作台的 `originalSkillsDirectory` 配置可随现有 profile 保留，读取时会丢弃。仅通过旧工作台目录登记的技能需要由用户在 DSH 中完成注册后才能执行条目化。

## 当前任务如何执行

ItemizationPanel → owner-only workbench/itemization → ItemizationService → DshItemizerRuntime → `standard` preset 的独立 Agent Session。任务按项目目录及执行 preset 读取 `requirement-itemizer` 的正文和资源位置，并作为单独的已记录上下文提供给 Agent。

兼容工具与角色名称只在插件中映射：

| 原接口或角色 | Harness 实现 |
| --- | --- |
| read_file | read，沿原生工具策略执行 |
| write_file | write，沿原生工具策略执行 |
| execute_shell_command | `shellToolName` 指定工具；本机为 pwsh |
| chat_with_agent | 托管子 Agent，等待实际完成或失败 |
| requirement_index_parser | DSH 注册的 `requirement-chunk-segment` |
| requirement_document_extractor | DSH 注册的 `requirement-chunk-extract` |

原生工具仍可用，文件与 Shell 别名通过 Harness 公共工具执行管线保留策略、审批及沙盒处理。子 Agent 由配置的 spawn 后端管理，父任务取消或插件卸载时取消并等待其结束。没有安装 CoPaw 运行时；兼容层覆盖当前条目化涉及的接口和两个角色。安装其他技能不代表阶段 5–9 已接入面板，也不代表其全部外部接口已适配或验证。

Agent 自行执行原技能步骤、读取与写入文件、运行脚本和修正问题。旧的 itemization_read_source、itemization_submit_chunks 以及三次提交计数已从当前执行器移除。总运行时限、模型输出预算、原生策略及子 Agent 调用自身的超时仍然生效。

## 面板发送的提示词

首次条目化采用手册第 3 页模板，替换路径占位符：

```text
请使用 requirement_itemizer 对系统需求文档进行条目化。
原始文档：<原文快照的绝对路径>
MinerU Markdown：<同版 Markdown 快照的绝对路径>
项目根目录：<本次 candidate 目录的绝对路径>
要求：按系统功能拆分为独立 Markdown，保留功能概述和系统概述；
从功能概述、功能列表或正文的明确描述中提取项目级 includes 关系；
不要根据目录层级推断包含关系。
请输出 chunks.json、每个功能条目、关系种子和校验结果。
```

新版本采用手册第 4 页模板：

```text
请重新条目化该项目的新版本文档，并与现有项目结果比较。
原始文档：<新版本原文快照的绝对路径>
MinerU Markdown：<新版本 Markdown 快照的绝对路径>
项目根目录：<已有结果目录的绝对路径>
请列出新增、删除、改名和需要重新建模的功能；重新校验 includes 关系及其原文证据。
不要覆盖旧版本产物，先输出差异报告。
```

调整没有独立的逐字模板，使用手册第 2 页通用模板填写流水线、输入、项目根目录、目标、要求输出和限制；具体文字见 `src/host/itemization-prompts.ts`。用户填写的调整意见单独记入 Session，不混入技能正文。

技能加载成功后，运行保存 `workbench-runs/<runId>/prompt.txt`（任务模板）、`execution-context.txt`（技能正文和任务上下文）、`execution.json`（模型、preset、预算、技能提供方、资源位置及正文摘要）。Session 分别记录 `workbench-original-skill`、`workbench-itemization` 和可选的 `workbench-itemization-feedback` 输入。

执行 Session 的初始工作区目录保持项目根目录，以符合宿主的工作区归属规则；关联完成后通过 WorkingDirectory 服务切换到本次 candidate 目录，该变化写入 Session。技术上下文同时提供本地图片引用与输入快照路径的对应表，供原技能复制资源；导入时只接受已登记引用，或内容摘要属于输入快照的现有图片，不根据名称猜测来源。

## 产物和审核

Agent 输出位于本次 `workbench-runs/<runId>/candidate/`，允许原技能在其中创建项目子目录。Host 查找唯一的 chunks.json，读取其功能路径及同目录 requirement_relations.json。原始 chunks.json、Markdown、关系与技能报告保持原样；面板另外生成 panel-content.json、index.json 和运行级 validation.json。缺少关系文件时单独生成 panel-relations.json 并阻止采用，不补造关系；缺少必要功能 Markdown 时运行失败，部分产物保留。

运行级 validation.json 的 `validationScope=artifact-import` 仅表示产物能否导入页面，不能代替原技能自身的覆盖、目录、内容或业务校验。原技能过程、脚本输出和自有报告在执行 Session 及产物中查看。原始 seed/关系文件中的 consistency_issues 保留为审核阻断；不会因为结构可读就清空。

「测试009」的 V1 报告保留原文冲突，profile 的 `reviewHolds` 保留此前的暂缓决定。2026-11-14 用户授权将当前 V1 候选用于阶段 5 开发，`candidateApprovals` 仅放行该项目的指定候选。用户在面板比较并确认影响后采用，Host 仍核对修订以及材料和产物指纹。 [候选与采用步骤](阶段验收/阶段04-P01-P02-P04.md#本轮收尾结论)

run.operation 和候选索引中的读取路径是可选字段，新代码可读旧记录。降级前请确认目标版本支持现有记录格式。

## 交给用户执行的验证

先在插件目录构建并检查。相邻宿主应已有与当前 checkout 匹配的构建产物；这些命令本次均未运行：

```powershell
Set-Location E:\dsh-sidebar-workbench
pnpm run build
pnpm run build:check
pnpm test
pnpm run test:artifact
git diff --check
```

确认旧 Host 没有正在执行的任务后，由用户正常停止旧进程，再按已有 profile 启动；不要附带 `--from-default-profile`，避免重置配置：

```powershell
Set-Location E:\deepseek-harness
pnpm dsh --profile sidebar-workbench-dev --port 3182 --no-open
```

使用该次启动日志的本地 URL，刷新页面，在已有“测试009”工作区、对应 Session 的工作台中验证：

1. 在执行 preset 的技能入口确认 `requirement-itemizer`、`requirement-chunk-segment` 和 `requirement-chunk-extract` 已由用户注册并允许模型使用。
2. 从面板开始 V1 条目化，记录新 runId 和执行 Session ID；检查 prompt.txt 与手册模板一致，execution-context.txt 含完整原技能，使用的是预期模型和 standard preset。
3. 查看执行 Session：Agent 可以使用文件、pwsh 和 chat_with_agent，两个子角色获得完整对应技能；脚本错误能返回 Agent 继续处理，不出现旧的 Candidate submission budget exhausted。
4. 查看原始 chunks.json、功能 Markdown、关系种子、requirement_relations.json、原技能的校验输出与页面摘要；分开判断导入成功、原技能校验结果和业务结论。
5. 输入调整意见再运行，检查父候选引用、新运行目录与旧产物指纹；旧结果和材料不应被覆盖。
6. 核对 V1 的已记录问题。当前获准采用的候选可在比较和影响确认后采用，其他受暂缓决定约束的候选需另行审核。取消任务后检查父子 Agent 均结束，再检查重启后的作业与候选状态。
7. V2 提供后，先确认已审核的上一版基线，再核对手册新版本模板、差异报告、采用结果与旧版产物。 [V2 验收步骤](阶段验收/阶段04-P01-P02-P04.md#v2-到位后的验收步骤)

首次真实模型运行需核对 Python、PDF/DOCX 解析、技能资源路径、凭据、网络和子 Agent。

受控浏览器入口为 `scripts/browser-itemization.mjs`。在隔离 home/profile 使用 `tests/fixtures/itemizer-provider.overlay.yml`，先在该 profile 注册 `requirement-itemizer`，再设置 `DSH_TEST_ITEMIZATION_EXECUTE=fixture`。该夹具写入固定产物，用于验证 Agent、文件工具和审核通道。会话采集规则见 [tests/expected/README.md](../tests/expected/README.md)。

## 配置与回退

当前目标 profile 使用 `executionPreset: standard`、`shellToolName: pwsh`、`subagentProvider: spawn`、`maxSubagentDepth: 4`、`operationTimeoutMs: 3600000`。需要自定义委派角色的技能时，在 `agentSkillAliases` 中填写对应的 DSH 注册名。

代码回退需构建目标旧版本，并使用与该版本兼容的工作区和 Host 存储。早期构建通过工作台的 `originalSkillsDirectory` 注册技能，当前构建通过执行 preset 的 DSH 技能注册表读取技能。
