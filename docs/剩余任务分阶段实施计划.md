# 剩余任务分阶段实施计划

## 摘要

本计划按页面组织工作，以“页面可操作、真实业务已联通、产物可核验、用户人工审核通过”为阶段完成标准。业务顺序依据[使用手册](使用手册.pdf)：项目与材料准备 → 条目化及版本审核 → 单功能建模 → 关系检查与对齐修订 → 测试生成 → 本地图谱校验 → 远端上传、推理和只读查询。阶段 1–2 的已验收成果保留，后续每阶段交付后停止，收到明确人工通过结论后才推进。

用户于 2026-10-29 明确确认“目前阶段2已完成，并通过我的人工验证”，并要求改为按页面交付真实业务。本次仅修订计划和关联说明，不启动阶段 3，不把计划要求记为已实现能力。阶段 3–10 均未开始。

## 1. 依据与范围

### 1.1 文档职责

[使用手册](使用手册.pdf)定义业务场景及交接条件；[集成方案](三条流水线集成方案.md)定义 S01–S10、工作区绑定和状态语义；[界面规范](三条流水线-界面与交互规范.md)定义 P00–P08；[任务书](三条流水线-Agent实施任务书.md)保留 A01–A28 验收矩阵。本计划是当前阶段顺序、真实接入范围和审核状态的唯一维护入口。原 T00–T05 作为任务分类和历史报告标识保留，不再要求先完成全部页面、再集中接入真实业务。

原八阶段计划中“阶段 3 仅验证 demo 交互”“阶段 4–7 才接编排、Host 和资源”“真实业务留待专项任务”的安排已被本计划替代。旧阶段报告记录当时实际证据，其中旧阶段编号按第 5 节映射，不据此启动旧任务。阶段 1–2 已通过不代表 A01–A28 全部通过，也不证明真实流水线已经可用。

手册以 QwenPaw 对话为入口；DSH 实现保留其输入、产物、限制与审核条件，不照搬运行接口。`requirement_itemizer`、`requirement_document_parse`、`requirement_analysis_pipeline`、`requirement_ontology_manager` 等名称须映射到实际可用的 Agent、Skill、脚本或服务，不能仅凭同名认定已接通。手册要求用户提供同版 MinerU Markdown；自动运行 MinerU 不属于本轮必需功能。

### 1.2 实现与数据范围

源码、测试和文档变更限制在 `E:/dsh-sidebar-workbench`；`E:/deepseek-harness` 仅用于公开 API 核对与运行验证。保留 tab ID `dsh-plugin-sidebar-workbench`、kind `sidebar-workbench`、安装方式、既有数据及未提交修改。一个 DSH Workspace 对应一个建模项目，根目录继承 `Workspace.path`，不增加独立项目选择器或可编辑输出根目录。

本计划纳入真实条目化、原文解析、四类 DSL 生成与复验、测试生成、TTL 转换、GraphDB 上传/推理/查询所需的业务接入和缺失实现。优先复用可核验的现有能力，按阶段补齐适配器、输入输出验证与执行逻辑；业务规则或源包缺失时列出具体缺口，不用演示数据或未经定义的规则替代。新增外部源代码修改、宿主扩展或安装部署超出当前范围时，先交付缺口与最小方案供用户决定。

完整可视化 DSL 编辑器、Excel 编辑器、通用 DAG 编辑器、自动清库、仓库重建和 TBox/SHACL 覆盖不在范围内。模型以真实源文件、追溯和修订请求为主；图谱关系表必须可用，图形展示可按能力增强。

真实验收使用隔离 home/profile、独立工作区、真实有效的样本文档和隔离 GraphDB 仓库。样本规模可以小，但不得用伪 PDF、固定返回值或模拟文件冒充真实业务。原始文件保持只读，候选与历史产物分别保存。凭据不写入文档、URL、日志、截图或导出文件；不重置日常 profile，不删除既有数据，不停止无关服务。

## 2. 推进与验收规则

### 2.1 阶段推进

执行顺序为“实施当前阶段 → 自检真实业务 → 提交页面、产物与操作步骤 → 等待用户人工审核 → 开始下一阶段”。本次改计划不等于启动实施；后续由用户明确启动新阶段 3。每次审核最多放行紧接的一个阶段，阶段 9 的三个子阶段也分别停止审核。没有回复、检查通过或截图生成均不能代替人工通过。

允许为当前页面实现它必需的共享服务和配套页面；不得借依赖提前完成后续未获准的业务。需要回改已验收行为时，说明影响，补做回归并提交人工复核。外部能力、模型访问、有效材料、业务规则或授权不足时，阶段记为“阻塞，未通过”，列出缺项和恢复条件，不能降级为 demo 验收或继续依赖阶段。

GraphDB 追加和推理的计划范围不等于一次具体写入授权。真实操作前由 P08 展示目标仓库、输入指纹、版本、作用范围及操作类型，取得对应明确授权；上传授权不包含推理。只读查询不触发上传或推理。有效授权范围未变时不重复确认，范围变化必须重新确认。

### 2.2 每阶段共同通过标准

下列标准适用于该阶段明确交付的页面操作，缺一项即不能宣布完成；尚未轮到的操作保持明确未接入，不计入该阶段的已交付范围。

1. **页面完成：** 入口、输入、前置条件、加载、成功、失败、取消或不可用原因、结果查看和返回路径完整；语言、主题、窄栏和键盘交互符合既有规范。
2. **真实调用：** 页面动作经过 Client、Remote、Host 到实际文件服务或业务执行器。运行 ID、输入版本、执行记录和状态可关联，不能以 Client 内存状态或手工推进代替实际运行。
3. **真实产物：** 必需文件或服务回执确实存在，结构与业务校验通过；页面能访问允许范围内的产物并定位对应原文、需求、模型或测试。下一阶段直接复用已经审核的输出，不靠手工替换示例文件衔接。
4. **数据与失败处理：** 本阶段成果和采用状态持久化，刷新恢复到正确项目。涉及长任务时验证关闭视图、断连、Host 重启、重复请求、取消确认和晚到结果；未知结果先核对，已提交事实不被失败或取消抹去。
5. **范围与授权：** Host 验证项目、工作区、绑定修订、文件范围及调用者权限；前置条件失败阻止下游，原文和旧产物不被覆盖。缺少能力时拒绝该操作，其他已接通操作按各自能力继续可用。
6. **人工审核：** 提供可重复的输入、操作步骤、预期结果、实际观察、运行与产物位置；用户明确通过后记录日期和放行范围。Agent 技术自检与用户对业务内容的审核分别记录。

单元测试、显式 demo 和测试适配器可覆盖异常路径，但均须标记证据类型，不能替代真实能力的成功路径和主要业务结果验收。未触发的真实故障不宣称已实测，记录受控故障测试与剩余限制。

## 4. 各阶段实施要求

以下是待实施要求，不代表已有能力；阶段 1–2 的实际工作与限制保留在原报告。后续阶段只有满足第 2.2 节和本节专属条件才可交付人工审核。

### 阶段 3：P00 项目与材料准备

**输入与前置条件：** 阶段 2 已通过；用户授权启动阶段 3；可访问的 DSH 工作区、真实 DOCX/PDF 和同版 MinerU Markdown。开始时复核当前插件、宿主、公开 API 和已有数据格式。

**页面与真实接入：** 完成初始化、只读识别、确认采用、重新关联、字段校验及冲突反馈；使用真实 Host 文件与绑定服务保存项目、材料版本和可识别成果索引。检查可读性、格式及来源；用户同版声明不等同内容一致性校验。P01 显示真实项目、材料和已登记成果，后续业务入口如尚未实现则明确不可执行。初始化进入流程准备页不宣称已运行条目化。

**同时交付：** 项目清单原子保存、唯一绑定、部分写入核对、资源读权限及路径校验；覆盖同工作区多会话、改名/移除、目录丢失、重新登记、迁移、复制身份与嵌套项目。先建立已识别格式的索引和必要预览，不伪造未知格式的验证结果。形成真实能力清单，列出各手册角色的实际源包/入口、版本、依赖、配置、输入输出及探测结果；尚缺的源包、服务、模型或规则列为后续阶段前置条件，不能只记录角色名。

**验收与产物：** 用户从 P00 登记有效材料，刷新后仍能访问同一项目和材料；识别不修改原件，采用结果可追溯，重复初始化不产生新身份；无归属、同步中、不可读与身份冲突分别处理。交付项目清单、材料/成果索引、能力核验清单和实际操作记录。真实文档内容解析由阶段 4 完成。

**停止点：** 阶段 3 待人工审核，通过后才进入阶段 4。

### 阶段 4：P02 真实条目化与版本审核

**输入与前置条件：** 阶段 3 已通过；有效同版材料及一个用于比较的新版本；条目化执行器已核验。缺失实现须在本阶段补齐，不能以导入预制结果代替运行。

**页面与真实接入：** P01 发起真实条目化，P04 展示实际过程，P02 展示概述、功能条目、关系种子和校验问题。支持提交调整意见后重新划分；新版本保留旧产物，展示新增、删除、改名、内容变化、关系变化及待匹配项，确认影响范围后采用。

**同时交付：** 首个真实运行通道、状态同步、输入/输出快照、版本与采用持久化、产物预览、幂等、取消与恢复。执行会话按工作区创建/关联；Session 切换和 `cd` 不改变运行目录。绑定失效停止依赖步骤；关闭视图不取消任务，Host 重启核对未终结任务，卸载按依赖顺序释放资源。后续阶段复用这些服务。

**验收与产物：** 实际生成并检查 `chunks.json`、系统/功能概述、功能 Markdown、`project_relation_seed` 及校验结果；种子具体扩展名以实际输出为准。每条 includes 有原文证据，不从目录层级推断。未审核候选不能成为下游基线；采用及影响清单刷新后保留，旧版仍可访问。用户完成一次首次条目化、一次调整和一次新版本比较/采用，核验 S01–S02。

**停止点：** 阶段 4 待人工审核，通过后才进入阶段 5。

### 阶段 5：P03/P04/P05 单功能解析与 DSL 建模

**输入与前置条件：** 阶段 4 已采用的功能条目与项目基线；已核验的解析、DSL 生成、语法及统一校验能力，以及所需模型配置。

**页面与真实接入：** P03 从真实功能清单搜索、筛选、选择并发起单功能建模；P04 展示阶段、问题和产物，P05 按 Environment、ExternalScenario、Statechart、DialogMap 查看真实模型、原文与需求映射。页面、执行记录和文件使用同一功能、版本与运行身份，不显示固定示例内容。

**同时交付：** 原文解析、关系增量、四类 DSL 生成与基础验证，受控的项目关系合并和版本冲突处理；模型及需求源文件的只读预览/定位、产物验证及旧结果失效。阶段 5 对外标明“建模至 DSL”；测试尚未接入时不得把“完整建模”或全流程标为完成。

**验收与产物：** 实际生成 `requirements.json`、实体、if-then、`relation_delta.json`、四类 DSL 和 `requirement_dsl_map.json`，核验可测试需求的定位及断言信息。项目关系增量保留来源、责任范围和提交版本，不能依靠共享信号猜测依赖。用户能从需求定位 DSL、原文及校验问题；原文不变，失败明确停止依赖步骤。本阶段只覆盖 S03 的解析/建模部分。

**停止点：** 阶段 5 待人工审核，通过后才进入阶段 6。

### 阶段 6：P05 关系检查、修订与对齐复验

**输入与前置条件：** 阶段 5 的模型与映射；包含关系遗漏、语法或对齐问题的有效样本；真实关系检查与对齐能力。

**页面与真实接入：** 从 P03/P04/P05 发起关系检查和对齐复验，按条目呈现原文依据、遗漏、差异、修订请求和待人工确认项。只允许原文唯一确定且可验证的内容写回 DSL；不靠删除条件换取通过，不把未经校验的文本编辑当成正式模型。

**同时交付：** 修订版本、校验/对齐状态、待办与新鲜度管理；关系增量合并冲突不得丢失已有项目结果，模型修订使受影响测试和 TTL 失效。所有修改记录关联到原始输入和复验结果。

**验收与产物：** 用户重现一次关系遗漏检查和一次对齐修订，查看 `relation_delta.json`、`alignment_result.json`、`alignment_report.md`、`completion_plan.md`、`alignment_changes.md` 及修订后的 DSL；具体额外产物按执行器协议登记。无法唯一确定的内容进入待办，未解决问题不能伪装通过。覆盖 S04–S05，输出满足后续测试前置条件的已审核模型样本。

**停止点：** 阶段 6 待人工审核，通过后才进入阶段 7。

### 阶段 7：P06 测试生成与完整建模闭环

**输入与前置条件：** 阶段 6 通过语法、统一校验和对齐的 DSL、原子需求及映射；真实测试生成器；至少两个功能用于批量验证。

**页面与真实接入：** P06 展示真实用例、覆盖映射和未覆盖项，支持重新生成、历史版本标记、Excel 打开/下载及需求追溯。P03/P04 接通从条目到测试的完整建模和批量队列，显示提交范围、阻塞项及配置化并发上限。

**同时交付：** 测试生成前置检查、产物内容与映射校验；逐功能运行、部分失败及局部重跑；并发关系增量提交和幂等，避免一个失败功能损坏其他已完成结果。批量能力在本阶段完成，不在前面仅凭多选 UI 宣称可用。

**验收与产物：** 实际生成 `testcase/测试用例.xlsx` 与 `testcase/requirement_testcase_map.json`，文件可打开，映射可读，每个可测试 `requirement_id` 有实际断言及 DSL/原文追溯。覆盖率列明分母和不可测试项理由，不能按文件数量估算。语法/统一校验/对齐失败、partial/missing、过期或未覆盖断言均阻止正式生成；受控失败测试与真实成功运行分别记载。用户完成单功能全流程、仅重生测试、批量及失败后局部重跑，至此才认定 S03 与 S06 完整通过。

**停止点：** 阶段 7 待人工审核，通过后才进入阶段 8。

### 阶段 8：P07 本地关系与 TTL 校验

**输入与前置条件：** 已验证 DSL、当前项目 `requirement_relations.json` 及其版本；真实转换器和本地 Turtle 校验器。

**页面与真实接入：** P07 展示本地关系列表、范围、统计、原文证据及纳入/排除原因；执行 TTL 转换并展示真实报告与下载入口。区分原文事实和未来推理结果，不自动连接或写入 GraphDB。

**验收与产物：** 实际生成 ABox TTL、转换统计、本地校验结果和问题列表；核对项目范围、版本、实体/关系和来源。以可观察的调用或网络证据验证本地操作不连接 GraphDB，不能用界面文字或 `committed=false` 代替。用户可从关系定位来源及模型，取得可交给阶段 9.1 的已验证 TTL，完成 S07。

**停止点：** 阶段 8 待人工审核，通过后才进入阶段 9.1。

### 阶段 9：P07/P08 远端操作

本阶段分三次交付和人工审核，按 9.1 → 9.2 → 9.3 顺序推进。开始前核实可访问的隔离 GraphDB 仓库、实际协议、凭据和规则版本，不将手册示例地址或仓库名当作用户的已授权目标。

#### 阶段 9.1：追加上传与验证

**输入与真实接入：** 使用阶段 8 的已验证 TTL，并核验目标仓库及所需 SHACL 规则已经就绪；缺失时先补齐前置条件，不通过覆盖仓库规则绕过。P08 展示操作、目标、项目版本、输入指纹、范围及限制；用户批准后，Host 再验证授权并仅追加本次 ABox，读取真实回执及 SHACL 验证结果。

**验收与产物：** 返回实际上传状态、三元组数量、中文标签抽样和 SHACL 报告。验证无授权不写、目标/输入/范围变化使授权失效、不清库、不覆盖 TBox/SHACL、不隐式推理。提交成功但验证失败时同时保留两个事实并阻止依赖推理；响应丢失先核对，不盲目重传。报告区分真实成功证据与故障注入证据，完成 S08。

**停止点：** 阶段 9.1 待人工审核，通过后才进入阶段 9.2。

#### 阶段 9.2：依赖与冲突推理

**输入与真实接入：** 核验 ABox、TBox、SHACL 的准备状态、版本及核验时间；缺少规则或检查失败则阻塞。P08 取得独立推理授权后执行真实业务规则，P07 分别显示原文事实与推理结论。

**验收与产物：** 返回依赖、写冲突、状态机问题及关系证据；每条推理关系具备 `relationSource`、`relationTarget`、`isInferred=true`、`subtype`、`evidence`。用已知有/无关系的样本核对，不能将同名信号、共享连接或目录层级单独视为依赖。记录实际准备状态、授权、执行和结果，完成 S09；零结果可有效，但须有可解释的样本预期与运行证据。

**停止点：** 阶段 9.2 待人工审核，通过后才进入阶段 9.3。

#### 阶段 9.3：只读查询与导出

**输入与真实接入：** 对已存在的项目关系查询，不要求当前用户先授权上传或推理。P07 支持来源/功能/关系筛选、证据详情、统计与 JSON 导出，并区分本地关系、GraphDB 关系和推理结果。

**验收与产物：** 导出关系类型、起点、终点、证据、置信度及统计；置信度缺失明确表示，不补造数值。核对真实空结果与连接/查询失败的区别，用实际请求记录验证只读、不上传、不推理、不修改仓库。至少包含一个有结果的查询及一个空结果查询，完成 S10。

**停止点：** 阶段 9.3 待人工审核，通过后阶段 9 才完成，随后进入阶段 10。

### 阶段 10：P00–P08 联合验收与交接

**验收与交付：** 汇总 A01–A28，完成跨页面、语言/主题/窄栏/键盘、会话切换、刷新、恢复、权限和资源访问回归。交付当前 README、配置与真实执行入口说明、运行及产物索引、逐项人工结论和交接文档。手册“三份阶段映射”具体文件名仍需按已验证能力明确，不猜测第三个名称。未验证的读屏、触摸或其他平台能力单列，不能把未完成的必需条目转为已通过。

**停止点：** 阶段 10 待人工审核；只有范围内条目完成并获得人工通过才能标记计划完成。本计划不自动触发提交、推送、打包发布或生产部署。
