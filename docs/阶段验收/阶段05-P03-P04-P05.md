# 阶段 5 单功能建模至 DSL

交付 P03 功能列表、P04 运行详情和 P05 原文与模型预览，覆盖 S03/A04 的解析和 DSL 部分。状态恢复、运行控制、资源隔离与既有页面回归参照 A13–A19、A23–A27。已读到「测试009」V1 的正式采用记录，修订为 3。已知 V1 原文冲突及阶段 4 的真实 V2 验收保留原记录。

## 如何验证

1. 在隔离的 DSH home 和 profile 安装当前构建。按 README 注册六个技能及其资源，并确认执行 preset 能选择真实模型、配置的 Python 能导入 textX。
2. 使用 [真实运行脚本](../../scripts/browser-modeling-real.mjs) 分别设置 `DSH_MODEL_SAMPLE=vehicle` 和 `DSH_MODEL_SAMPLE=radio`。以当前隔离 Host 的本地 URL 设置 `DSH_TEST_URL`，为每个样本指定全新 `DSH_TEST_OUTPUT_DIR`。将 `DSH_MODEL_SOURCE` 分别指向原「测试009」和「测试结果001」目录。用 `node scripts/browser-modeling-real.mjs` 启动。脚本读取原材料并在独立工作区执行。车辆样本复用已采用 V1 产物，副本以独立项目 ID 注册。收音机样本从 PDF 与同版 MinerU Markdown 执行条目化，尝试在隔离项目采用通过审核门槛的新候选。
3. 在流程页点「功能列表」，搜索并选中功能。确认基线与功能名称后点击「建模至 DSL」。在运行详情记下运行和关联对话，核对每个阶段及校验报告。刷新后重新打开同一运行。
4. 在模型页按 DSL 类型查看源文件，选择一个可测试需求查看原文行号、模型元素和断言。人工确认断言对应原文的预期结果。核对关系仅使用原文证据、待确认关系仍可读，原件与基线指纹保持一致。对照「转毂模式」的适用范围及「收音机」的页面、控件、跳转。

## 状态和校验证据

Client 经 owner-only `workbench/modeling` 调用 Host。在独立执行 Session 记录各阶段提示词。Host 校验需求契约、实体表、IF/THEN 归属、关系证据、四类 grammar 和 DSL 引用，然后追加同一条模型与关系发布记录。首次运行不需要预置建模记录，旧条目化记录按现有格式读取。

文件保存在 `workbench-runs/<runId>/`。其中 `execution.json` 为技能、模型、Python 与资源摘要，`checks/` 为实际校验输出，`validation.json` 或 `failure.json` 记录结果。项目采用的模型与关系位于 `.workbench/modeling/` 对应的发布代次。覆盖缺口会写入 `requirement_dsl_map.json`，由阶段 6 对齐。

受控测试覆盖无基线及错误工作区、请求去重、语法或引用失败后的旧发布保留、关系版本冲突、重跑替换、受控换版后过期、取消、重启核对和待覆盖断言。浏览器冒烟与生命周期验证在独立 Host 上执行，涵盖现有条目化入口、演示、语言主题、窄栏、Session 和草稿隔离。使用仓库 Playwright 脚本，本会话未列出 Browser skill。DeepSeek 账号资料读取 403 收录在浏览器报告中。
